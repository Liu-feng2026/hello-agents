# Spider Craft

## 分工边界

本 skill 只写两类内容：

1. **决策方法论**：什么情况下走哪条路线、如何判定、如何验证。
2. **编排约束**：chrome-devtools 与 js-reverse 的串行协作方式、证据落盘、NoteTool 状态维护。

不复述工具调用方式（MCP 描述已对模型可见）；补环境的执行细节见官方 `mcp-js-reverse-playbook`，本 skill 只负责"何时走补环境"的路由判断。

## 核心原则

1. **先证明，再推断**：关键结论必须有请求、响应、代码或运行结果作为证据。
2. **先恢复单个稳定请求**：核心请求稳定前，不扩展分页、并发和批量采集。
3. **浏览器只用于取证**：最终重放与采集不依赖实时浏览器页面；可保留经验证的最小本地 JS/WASM 辅助。
4. **HTTP 200 ≠ 业务成功**：必须验证响应中包含有效目标数据。
5. **不硬编码未证明的旋转状态**：确认生成位置、写入位置、作用范围、有效期和刷新方式之前，不得硬编码 Cookie、Token、签名或计数器。
6. **启动请求不是业务请求**：“web-config”、APM/埋点、“sysDict”、字典、静态资源等只用于环境诊断；它们失败、挂起或页面因此报错，均不能作为任务结束理由。

## 分层诊断主流程

整个流程的骨架是**分层拆变量**：Step 2 在浏览器内消融，把「参数被校验」和「传输被校验」分开；Step 5 只在前者排除、后者仍然失败时介入。

### Step 0：入口分类

- **live-target**：只有目标网站，从在线页面开始取证。
- **artifact-only**：已有 HAR、JS、请求日志等离线材料，优先离线分析，不为形式打开浏览器。
- **continuation**：先用 NoteTool 检索同目标 `task_state`，从第一个未完成 Step 恢复，不重复已完成的取证。

### Step 1：取证抓真实请求

用 chrome-devtools 抓到目标数据对应的真实业务请求：URL、Method、Headers、完整 Cookie、Body、响应结构、initiator。区分诱饵接口与真实接口。证据落盘并创建 `evidence` 笔记。

**任务前提复核**：任务描述中声明的接口 URL/参数名只是线索，不是事实。
1. 在页面实抓流量或前端 bundle 中检索声明接口的路径字符串；
2. 字符串零命中 → 声明的接口不存在于当前前端，以实抓到的真实请求为准，在 task_state 记录"声明 vs 实抓"差异并在报告中说明；
3. 遇到 524/限流类错误时，先对照浏览器同一请求此刻是否成功，再决定等待还是换道；
4. 页面空白/302 不代表站点不可用：等待、重试、换入口后再判，不得因首屏失败直接转入纯离线分析。

**启动链路异常时的继续规则**：
1. 先把异常请求标注为启动配置、字典、监控或其他非业务请求，不得误当作目标接口；
2. 用户已给出接口线索时，继续在前端 bundle 中搜索接口路径、函数名和参数名，并对该接口做独立取证；
3. 用户未给出接口时，继续搜索与目标数据/功能对应的路由模块和请求构造代码；
4. 只有已定位的真实业务接口也无法访问，并已记录该接口的 URL、Method 与失败证据时，才可声明阻塞；否则继续执行。

## 已确认业务接口锁定 Gate

一旦在 Network 中实抓到同时满足“目标数据对应、请求成功、响应含有效目标数据”的业务请求，它就是当前任务的**唯一主接口**。立即把其 URL、Method、请求样本和证据路径写入 `task_state`，并直接进入 Step 2。

1. 锁定后，禁止为了“多找几个接口”再导航、evaluate、请求或重放任何候选接口、猜测接口、启动接口、字典接口或旁路接口。
2. 后续所有浏览器重放、参数消融、JS 跟栈和本地 Python 重放，必须只围绕该主接口展开。
3. 只有主接口的**浏览器原样重放失败**时，才允许回到 Step 1；先检查同一接口缺失的前置状态、会话或触发动作，不能因为失败就猜测或切换新的业务接口。
4. 旁路接口仅在已有证据表明它是主接口的必要前置依赖时才可检查；每项旁路检查限一次、使用独立短超时。失败只记录为辅助证据，不得改变主接口、清空已有主线证据、重置 Step 2，或成为整轮任务的阻塞理由。
5. 页面、CDP 或旁路调用异常时，优先恢复到可对主接口取证/重放的页面状态；恢复后仍继续主接口流程。

### Step 2：浏览器内重放 + 参数消融

目的：在不引入传输层变量的前提下，锁定**需逆向参数清单**。

1. 在浏览器内**原样重放**请求。成功 → 请求自包含，问题在参数层；失败 → 先排查未捕获的前置状态（bootstrap、会话建立链），不要急着消融。
2. 对每个变化参数做**消融**：重放时只把它固定为旧值或篡改值，其余保持新鲜值。固定后失败 → 被服务端校验 → **需逆向**；固定后仍成功 → 不被校验。
3. Header 和 Cookie 同样适用消融，不只 body/query。
4. 区分「被校验」与「仅影响结果」：翻页 cursor、页码是协议的一部分，需要正确构造，但不需要逆向算法。
5. 重复直到清单覆盖所有被校验的动态参数，写入 `task_state`。

详细方法见 `references/ablation.md`。

### Step 3：跟栈定位生成点

chrome 取证完成后交接给 js-reverse 重新打开目标、复现请求，跟栈定位每个需逆向参数的写入位置（writer）和生成函数。确认是否存在多个 writer、输入来自哪些状态。原始 JS 片段落盘保存。

### Step 4：三级分流重建

根据混淆程度和运行时依赖，为每个生成函数选择路线：

| 路线 | 判定信号 | 产出 |
|---|---|---|
| 纯算 | 无混淆/轻混淆，逻辑可读，不依赖浏览器 API | Python/Node 重写算法 |
| AST 反混淆 → 纯算 | obfuscator.io 特征、字符串表、控制流平坦化 | 还原后按纯算处理 |
| 补环境 | JSVMP/自定义 VM、重环境检测（canvas、navigator、storage） | Node 局部执行，缺啥补啥 |

快速判据看混淆；准确判据是 hook 住生成函数后看它实际依赖了哪些宿主对象。判定树见 `references/rebuild-routes.md`；补环境执行细节走官方 `mcp-js-reverse-playbook`。

任何路线都必须先固定样本对拍：保存一组已知输入 → 输出，本地实现与原始结果一致后才能接入重放。

### Step 5：本地重放对比（传输层）

本地 Python 重放成功 → 直接进 Step 6。**浏览器成功 + 本地失败 = 传输层差异**，按性价比排查：

1. TLS/JA3 指纹（cipher suite、扩展顺序）→ `curl_cffi` 的 `impersonate`。
2. Header 顺序与集合 → 同样可用 `curl_cffi` 按传入顺序精确控制。
3. HTTP/2 伪头部、Cookie 顺序 → 次常见，逐项对齐。

排查方法见 `references/transport.md`。

### Step 6：稳定性验证

1. 固定输入验证签名/解码 helper。
2. 同一会话链上完成一次最小重放。
3. 更换新动态值或新会话再次验证，建议连续成功 2～3 次。
4. 确认响应包含有效业务数据后，才测试分页、重试、并发、去重。

任一项失败：保留证据、更新 `blocker`，不把部分成功描述成完整采集器。

## 分页协议验收门（需要翻页采集时必做）

当目标需要分页、批量或断点续采时，单页成功只属于证据，不得作为协议恢复成功。

1. 在同一新鲜浏览器会话中抓取至少两次相邻页成功请求（例如 current=1、current=2），分别保存完整 URL、query、body、请求头、Cookie、响应头、状态、记录数和首条记录 ID。
2. 对两页请求做字段级 diff，明确分为：固定字段、页码或 cursor 字段、每请求变化字段、每会话变化字段、未知字段。Cookie、签名、时间戳、nonce、计数器、Referer 和请求顺序都必须纳入对比。
3. 对每个变化字段做最小验证：页码/cursor 只需正确构造；会话或每请求状态必须定位生成、刷新与写入位置。没有完成此项时，不得用第 1 页固定值重放第 2 页。
4. 协议版本的验收必须在新 requests.Session 或等价独立 HTTP 会话中连续请求第 1 页再第 2 页：两次均为有效业务 JSON、每页记录数正确、两页首条或 ID 集合不同。浏览器自动化、浏览器导出的历史响应、固定 Cookie 重放都不能通过此验收。
5. 仅在上述序列成功后实现分页循环、重试、去重和详情采集；分页失败时保存 pagination_diff、每次请求状态和失败原因。

### 三次恢复尝试上限

协议验收失败后，最多进行 3 次彼此不同且有明确假设的恢复尝试。每次先在 task_state 记录：假设、目标动态状态、拟修改的重建方式、验证页序列。每次结束记录实际结果。

三次仍未通过“新会话连续两页”验收时，停止协议恢复并报告未恢复成功；保留证据、差异表和失败记录。不得用浏览器成功、单页成功或固定 Cookie 成功替代验收。
## 旁路 Gate

主流程覆盖 signer（Step 2～4）与 transport（Step 5）。另外两类卡点：

- **verifier-gated**：Challenge、验证码、遥测侧车拦截业务请求 → 先冻结一条完整有序 transcript（init → sidecar → verify → 首个下游消费），盘点 sidecar 状态写入并做消融矩阵，之后才谈参数与轨迹调优。
- **decode-gated**：HTTP 成功但响应需本地解码 → 定位解码链（加密/编码/压缩/字形映射），固定样本对拍后用 Python 复现。

## 工具编排约束

1. chrome-devtools 与 js-reverse 对同一目标**串行使用**，不同时操作目标页面；chrome 阶段取证完成后才交接。
2. 交接时保留已确认的请求、状态和关键证据；无法重建的关键状态明确标记保留，不直接丢弃。
3. 工具返回完整请求、响应或关键 JS 后，先落盘 `tasks/<任务名>/evidence/`，再创建 `evidence` 笔记引用路径，不把长原文塞进对话或任务状态。

## 上下文体积纪律（历史会被机械淘汰）

上下文窗口是稀缺资源。历史轮次超过阈值会被**整轮机械淘汰**，淘汰后只剩结论和文件路径。以下纪律保证淘汰不丢事实：

1. **单条工具结果超过 ~10KB 即违规**：读文件前先看大小；大于 20KB 的文件禁止整读，用 `read_text_file` 的 `head`/`tail` 参数，或 python_repl 按行/字节区间切片读取（如 `show(start, end)`）。
2. **分析在本地做，结论回对话**：bundle 的正则扫描、diff、统计在 python_repl 内完成，只把简短的 stdout 结论带回来，不把原始内容复述进对话。
3. **结论即写即存**：每得出一个可复查的结论，立即更新 `task_state`。只存在于对话里的结论会随淘汰永久丢失。
4. **按路径回查，不靠记忆**：需要历史细节时从 `evidence/` 与 `tool-output/` 按路径回读切片，不要凭记忆推测已淘汰的内容。

## 换道纪律（防死磕）

同一假设在同一轮次内重复尝试 3 次、或连续两个假设在同一 Step 失败、或连续 5 步未更新 task_state 进度——即视为死磕，必须换道。

换道前写下四行（写入 `task_state` 的"路线判断"字段）：

1. 当前路线最新的可用证据是什么；
2. 当前路线的精确失败点是什么（报错/盲区/缺状态）；
3. 备选路线为什么是能回答该失败点的最小换道；
4. 已完成的取证在换道后是否仍然有效。

换道动作：更新 `task_state`（记录换道理由）→ 跳到对应 Step 重入（纯算→AST 反混淆→补环境；浏览器取证受阻→转 artifact-only 换证据源）。已落盘证据全部保留，不清空重头再来。

禁止：不写理由就换道；在同一路线上第 3 次尝试同一假设；跳级直上最重路线。

## 任务记录协议（NoteTool）

任务状态通过 NoteTool 维护，不依赖对话历史。

### 任务状态恢复

任务启动前，由外层运行器负责：

1. 列出已有 `task_state` 笔记；
2. 读取候选笔记内容；
3. 调用一次任务匹配流程判断是否存在可复用状态；
4. 将匹配到的 `note_id` 和完整 `task_state` 注入初始上下文。

如果没有匹配到历史任务，初始上下文必须明确标记“尚未建立 task_state”，由主 Agent 创建新的 `task_state`。

主 Agent 不应在启动阶段重复检索全部笔记；找到已有状态后，后续始终更新同一条 `note_id`，不得创建平行任务状态。

每个任务只维护一条主 `task_state` 笔记，内容包含：

- 目标与任务范围
- 当前 Step、各 Step 完成情况
- 卡点分类（signer、verifier、decode、transport）
- 需逆向参数清单及每个参数的处理状态
- 路线判断（纯算、AST 反混淆后纯算、补环境、传输层排查）
- 路线选择依据与当前结论
- 下一步动作
- 当前阻塞
- `delivery_level`
- 证据索引

证据原文不写入笔记。请求、响应、脚本和运行输出保存到任务目录，`task_state` 只记录可复查的文件路径和简短结论。

维护规则：

1. 新任务启动时先检索已有 `task_state`，找到可复用任务后读取其 `note_id` 并继续更新，不创建平行状态。
2. 找不到可复用任务时，用 `NoteTool.create` 创建一条新的 `task_state`。
3. 每完成一个 Step，都更新同一条 `task_state` 的 Step 状态、参数清单、路线判断、关键结论和下一步动作。
4. 验证事实后先将原文落盘，再把文件路径和简短结论写入 `task_state`。
5. 结束前回读 `task_state` 核对交付等级；未达目标不得宣称完成，仍有可验证的下一步时继续执行，否则记录阻塞和恢复 Step。

## 交付等级

1. **evidence**：可复查的真实请求、响应或代码证据。
2. **local-proof**：关键签名/解码逻辑在本地固定样本验证通过。
3. **compact-replay**：脱离浏览器独立重复执行目标请求。
4. **collector**：稳定重放之上支持分页、重试、去重、解析和输出。
