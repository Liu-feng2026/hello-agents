## Mission（目标）

将需要网页逆向的采集目标恢复为稳定、可验证、可重复执行的协议采集流程。

## Non-Negotiables（不可违反原则）

1. 先定位并证明真实业务请求，再进行分页、并发或批量采集。
2. 浏览器和逆向工具只用于取证；最终协议采集流程不得依赖人工点击或浏览器自动化，并优先使用 Python 实现。
3. 对 Sign（签名）、Token（令牌）、Cookie（会话状态）等动态状态，在没有确认其生成位置、输入、写入位置和刷新方式之前，不得直接硬编码。
4. 如果 JavaScript（JavaScript）或 WASM（网页汇编）逻辑直接改写为 Python 风险更高，可以保留最小本地辅助模块，但不得依赖真实浏览器页面环境。
5. 不能因为一次请求成功、HTTP 200、Token（令牌）非空或 Cookie（会话状态）存在就宣布完成，必须根据当前交付目标进行验证。
6. 当前只能达到 evidence（证据）或 local-proof（本地证明）时，必须如实标记，不能提前声称已经完成 Collector（采集器）。

## Intake（任务接入）

开始分析前，先判断当前任务属于哪种输入模式：

- `live-target（在线目标）`：需要对当前网站或接口重新获取真实请求和运行时证据。
- `artifact-only（仅离线材料）`：只有请求、抓包、源码、JavaScript、WASM、Token、Cookie 或响应样本等离线材料；仅基于这些材料进行本地分析，不启动浏览器，并将当前在线行为视为尚未验证。
- `continuation（继续任务）`：目标和关键环境没有变化，已有可信证据和任务状态；复用已有结果，只重新检查发生变化的部分。

## Triage（问题分类）

确定任务输入模式后，判断当前主要卡点：

- `signer-gated（签名卡点）`：请求字段或封装值需要重新生成。
- `verifier-gated（验证器卡点）`：Challenge（验证挑战）、warm-up（预热）、telemetry sidecars（遥测附加请求）或 verifier state（验证状态）挡住了业务请求。
- `decode-gated（解码卡点）`：HTTP 请求已经成功，但响应还需要本地解码。
- `session-gated（会话卡点）`：登录、配对、计数器、心跳、密钥、请求顺序或登录后的业务状态控制请求是否成功。

如果 TLS、HTTP 版本、UA（用户代理）或客户端网络栈等问题在业务逻辑之前就使请求失败，则额外标记为 `transport-gated（传输层卡点）`。

当 `signer-gated（签名卡点）` 涉及修改过的摘要或加密算法、固定输入验证，或者 JavaScript → Python 的位运算 / 字节处理差异时，读取 `references/crypto-patterns.md`。

## 通用逆向循环

### 阶段 0：识别协议特征
先判断真正接口、协议形态，以及当前主要卡点属于哪一类。

### 阶段 1：证明真实请求
找到真正的业务接口，并完整确认 URL、Method（请求方法）、Headers（请求头）、Body（请求体）、Response（响应）等。

### 阶段 2：隔离动态状态
找出 Timestamp（时间戳）、Nonce（随机数）、Sign（签名）、Token（令牌）、Cookie（会话状态）、Counter（计数器）等会变化并影响请求结果的内容。

### 阶段 3：定位真正的改写位置
找到这些动态值在哪里被生成、修改，并最终写入真实请求。

### 阶段 4：本地重建
把浏览器或网页运行环境中的关键逻辑逐步恢复为本地可运行逻辑。

### 阶段 5：证明可重复性，再扩展
重复请求验证成功后，再进行分页、并发或批量采集。

## 工具选择原则

- 根据当前证据缺口选择最小必要工具，不为了“走完整流程”调用无关工具。
- 多种工具都能完成当前任务时，优先选择范围更小、依赖更少、便于复现的方案。

## 交付等级

- `evidence（证据）`：找到真实请求、请求发起位置、状态来源、改写位置，或者明确指出当前卡点。
- `local-proof（本地证明）`：有固定样本验证、解码样本、还原后的源码，或者一个本地可调用的辅助模块，但还没有完成真实在线重放。
- `compact-replay（最小重放）`：针对已经证明的真实请求，提供一个范围明确、可以直接运行的最小重放程序。
- `collector（采集器）`：可以重复执行、不依赖浏览器的 Python 采集器。

## 验证标准

- 使用固定输入或固定响应样本，验证本地辅助逻辑、签名逻辑和解码逻辑是否正确。
- 在扩大采集范围之前，先成功完成一次新的真实业务请求重放。
- 真实在线请求至少重复重放 2～3 次；辅助模块能够运行、Token（令牌）非空或结果看起来合理，都不能视为验证成功。
- 根据实际采集目标继续验证下一页或 Cursor（游标）、状态刷新、字段完整性等。
- 只有验证通过后，才继续分页、并发或批量采集。

## 继续任务

如果目标网站、会话假设、可用工具、交付目标都没有变化，就复用之前已经确认的结果；只重新检查这次新输入真正影响到的证据部分。

如果准备重新开始一轮很长的逆向，先看看项目里是不是已经有同类目标的纯协议 Collector（采集器）或 Challenge（验证挑战）辅助模块，能复用就不要从头再做。
