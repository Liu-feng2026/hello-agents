# Spider Reverse

## 目标

最终目标是把浏览器中成功的数据请求，恢复成不依赖浏览器、可以重复执行的协议采集流程。

`chrome_devtools` 和 `js_reverse` 只用于寻找真实请求和分析阻塞问题，不作为最终采集方式。

## 工作流程

### 1. 找到真实业务请求

先使用 `chrome_devtools` 查看页面和 Network 请求，找到真正返回目标数据的请求。

然后使用 `js_reverse` 打开同一个目标页面，继续查看 Network、请求发起位置以及影响请求重放的动态状态。

如果 `chrome_devtools` 无法正常加载目标页面，但 `js_reverse` 可用，仍要继续使用 `js_reverse` 获取 Network 和源码证据；只有两个工具都无法获得有效证据时，才把浏览器取证视为当前阻塞。

两个工具按顺序使用，不要同时操作同一个网站。

重点确认：

- URL
- Method
- Query / Body
- Headers
- Response

### 2. 尽早尝试协议重放

找到真实业务请求后，先尝试使用普通 HTTP / Python 直接重放。

- 如果成功，进入重复性验证。
- 如果失败，找到当前最小阻塞点。

凡是声称某个 HTTP 客户端或协议路径已经尝试，必须有当前任务中的 `python_repl` 实际执行结果；未实际执行的尝试不能写入结论，也不能作为结束任务的依据。

如果验证某条协议路径所需的 Python 依赖缺失，而 `python_repl` 提供依赖安装能力，应先尝试安装；只有安装失败后，才能把该依赖缺失视为当前路径不可用。

不要因为看到复杂 JavaScript、混淆代码或 VM，就默认需要全部逆向。

### 3. 解决当前最小阻塞点

只分析当前阻止协议重放成功的问题。

常见情况：

- 请求中的值不断变化  
  → 检查动态参数、Token、签名。

- 同样请求换 Session 后失败  
  → 检查 Cookie、登录态或会话状态。

- 必须先经过某个页面或验证流程  
  → 检查 Challenge / verifier 产生的状态。

- 请求成功，但响应无法直接使用  
  → 检查解码、解密、解压或数据转换。

- 请求还没进入正常业务逻辑就被拒绝  
  → 检查请求头、UA、HTTP/TLS 或其他传输特征；必要时使用不同 HTTP 客户端做对照，例如 `curl_cffi`。

分类只是为了决定下一步查哪里。

每得到一个会影响后续判断的重要发现，记录：

- **现象**：发生了什么。
- **证据**：关键请求、响应或其他能够证明判断的信息。
- **结论**：当前确认了什么。
- **下一步**：接下来准备验证什么。

只记录关键节点，不记录无意义的操作流水。

确认阻塞点后，只继续分析与它直接相关的内容，例如它从哪里产生、在哪里写入请求、什么时候变化、有效范围是什么，以及如何重新生成或获取。

不要扩大逆向范围。一旦已经足够支持下一次协议重放，就停止继续深入并立即测试。

如果仍然失败，根据新的请求和响应重新判断当前最小阻塞点，然后继续这一过程。

### 4. 重复验证

协议重放成功后，至少验证 2～3 次，并尽量使用新的请求状态或新 Session。

确认：

- 请求能够持续成功。
- 返回的数据确实是目标数据。
- 必要的动态状态可以正常重新获取或生成。
- 采集流程可以脱离浏览器独立运行。

一次成功、一次 HTTP 200、一个暂时可用的 Token 或 Cookie，都不代表已经恢复成功。

浏览器能够采集但协议重放仍然失败，也不代表恢复成功，不要把浏览器自动化作为最终采集方案。

## 结束条件

出现以下任一情况时结束：

1. 协议采集已经能够脱离浏览器稳定重复执行。
2. 已经尝试当前可用、且与现有证据匹配的协议恢复路径，仍无法获得新的有效证据，或已证明存在当前环境无法解决的外部阻塞。

如果尚未满足以上条件，并且仍有明确、可验证且尚未尝试的协议恢复路径，就不要结束任务，继续从“解决当前最小阻塞点”开始分析并重新尝试协议重放。

如果结论中仍然存在“还需继续分析、还原或验证”的明确下一步，就不得结束任务。
