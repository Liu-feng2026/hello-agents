# 传输层对齐（TLS 指纹 / Header 顺序）

## 定位信号

浏览器内重放成功，业务参数在本地也已正确重建（Step 4 已对拍通过），但本地 Python 请求仍失败 → **传输层差异**。此时服务端校验的是客户端指纹，不是业务参数。

常见形态：403/412/418、返回风控页或 challenge 脚本、TLS 握手阶段被拒、连接被重置。

判定前置：先用相同参数在浏览器内再重放一次确认仍然成功，排除「目标刚好改版」和「参数重建有错」两个混淆变量，再进入传输层排查。

## 排查顺序（按性价比）

1. **TLS/JA3 指纹**：requests/httpx 背后的 OpenSSL 指纹与浏览器差异大（cipher suite 集合与顺序、扩展列表、ALPN、签名算法）。
   - 解法：`curl_cffi`，`from curl_cffi import requests; requests.get(url, impersonate="chrome")`，自动对齐 Chrome 的 TLS 与 HTTP/2 行为。
2. **Header 顺序与集合**：requests 按内部逻辑组装头，顺序、大小写、默认头集合都与浏览器不同，部分风控逐字节比对头部序列。
   - 解法：`curl_cffi` 的 `headers=` 按传入顺序原样发送；对照浏览器请求逐头对齐，包括大小写和无值头。
3. **HTTP 版本与伪头部**：浏览器走 h2（`:method`/`:authority` 等伪头部有约定顺序），requests 默认 http/1.1。
   - `curl_cffi` impersonate 默认启用 h2，通常随第 1 步一并解决；仍失败时显式对比 `http_version`。
4. **Cookie 顺序**：少数站点校验整个 Cookie 头的键顺序与分段，逐项对齐。
5. **行为指纹**：以上全对齐仍失败，考虑 IP 信誉、频控、前置 telemetry 未完成、账号环境差异——回到业务层排查，不要继续在传输配置上盲试。

## 对齐方法

1. 从浏览器 DevTools（或抓包）导出成功请求的完整原始头序列，按序重建 header 列表。
2. 用 `curl_cffi` 发送，diff 本地响应与浏览器响应（状态码、头部、体结构）。
3. 单变量切换定位最小条件：同一路径下对比 impersonate 目标（chrome/safari/firefox 各版本）、h1/h2、逐个增减头部，找到被接受的最小组合。
4. 不引入未经验证的额外配置（多余代理、多余头、多余 TLS 参数），避免「能跑但不知道为什么能跑」。

## 验证

1. 相同业务参数下，本地与浏览器响应逐字段一致，且包含有效目标数据。
2. 更换新的动态参数或重建连接后再次成功。
3. 连续 2～3 次稳定后，才把传输配置固化进 collector。
4. 传输适配与业务逻辑分层存放（如 `transport.py` 与 `client.py` 分离），便于目标换指纹时只改一处。
